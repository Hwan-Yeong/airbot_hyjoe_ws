## 개선 방향성
  - **`strategy 패턴` + `factory 패턴`**
  - "비슷한 역할을 하는 동일 계열 알고리즘 군 별로 관리" + "객체 생성 로직을 별도의 클래스나 메서드로 캡슐화하여, 클라이언트 코드와 직접적인 결합을 끊음"
    - 현재는 주 기능인 Converter 기능의 전략 하나만 구현. 추후 센서별 상태 및 에러 관리나 filter 전략 등을 추가할 수 있음
    - Client 가 new 로 직접 객체 생성하는 것 방지 + 코드간 의존성 감소 및 유연한 확장에 유리, 중앙관리 용이하여 필요한 기능 생성 여부 결정 및 적용 편리


## 개선 Point!
  - cpu 점유율 감소 (기존 : 동작/대기 상관없이 50~80 % 사용 <-> 변경 : 동작 시 70% 이하, 대기 시 20% 미만 사용)
  - 센서별 tf 발행 기능 추가로, Navigation 의 Obstacle Layer 알고리즘 수정/변경에 용이 (e.g. stvl)
  - 새로운 센서 추가 / 기존 센서 제거 등의 수정 및 관리 용이
  - 센서 extrinsic 배치 요소를 parameter화 시켜 개발단계에서의 센서 배치 변경 등에 대응하기 유리 (개발 및 테스트 시간 감축)

      2. 컴파일 타임 최적화와 의존성 고립을 위해...

      3. 가독성 및 변경사항 관리 용이성 향상을 위해...

  2. converter 가 node의 "공유 메모리"를 소유하고 있는 구조
      - (개선방향)
        - raw pointer 로 변경
      - (장단점)
        - Pros - 메모리 누수 위험 제거 / 참조 때마다 ref 카운팅 되는 현상으로 인한 오버헤드 위험 제거 /  객체의 생명주기를 관여하지 않고 "기능"만 빌려쓰는 의도로 코딩 (모던 cpp)
        - Cons - 부모인 Node가 먼저 메모리에서 해제되었을 경우 Dangling Pointer (seg fault로 죽음) -> ros2 특성 상 노드의 생명주기가 무조건 더 김!, 실제 발생확률 매우매우 적음
